# ADR 0005 — Recoverable MOCK authorize/reserve/capture checkout

Implement one supplier capability strategy, AUTHORIZE_RESERVE_CAPTURE, for the existing fictional flight providers. Explicit customer consent starts a durable versioned checkout from an owned accepted unexpired quote whose initial validation succeeded. Revalidation precedes authorization and new reservation calls. This is deterministic MOCK only; no card fields, hosted gateway claims, real funds, PNRs or real tickets.

Keep validation v1 immutable. Add `/api/v2/bookings/{id}`, `/api/v2/me/bookings` and `/api/v2/bookings/{id}/checkout`. Once checkout begins, legacy detail reads fail closed with an existing 409 BOOKING_CONFLICT instead of reporting NOT_STARTED. Legacy list status remains validation-only. Frontend reads v2. Existing quotes, intents, workflow definitions and event schemas remain unchanged.

Booking owns checkout orchestration, supplier observations and a versioned durable workflow. Payments owns MOCK payment accounts, immutable operation receipts and balanced capture journal entries. Communication uses published ports through adapters. Persist operation IDs and attempt/lease before calls; never hold an orchestration transaction across a payment/supplier call. Each effect is first looked up by stable operation ID. Only definitive absence allows a safely idempotent mock mutation. Lost responses and process death reconcile before any replay. Attempts are bounded per step, with database-clock leases, fencing and backoff; exhaustion yields REVIEW, not invented failure/success.

Reservation rejection voids authorization. Capture rejection cancels the supplier reservation before voiding authorization. Unknown capture outcomes are reconciled before compensation. CONFIRMED requires both supplier confirmation and captured payment in MOCK mode. Authorization expiry and quote expiry must not cause blind repeat effects. Refund-after-capture, cancellation initiated by customers, documents, real hosted gateways/webhooks and other supplier sequences remain separate P0 work.

Checkout changes write immutable lifecycle outbox records in the same local transaction. Their publication is tracked as pending work; existing validation event delivery continues independently. This deliberately does not claim an external message broker, notifications or complete Phase 5 production readiness.

Acceptance plan: AC-023 owned/consented/idempotent start and v1/v2 compatibility; AC-024 authorize/reserve/capture truth and balanced immutable journal; AC-025 reservation/capture failure compensation; AC-026 lookup-before-retry, actual crash/lost-response recovery and lease fencing; AC-027 expiry/price/ownership/CSRF and responsive browser recovery. All source P0 requirements remain tracked until complete across enabled providers.
